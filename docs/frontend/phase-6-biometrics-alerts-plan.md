# ECOS — Phase 6 Biometrics & Alerts Plan

## 1. Scope

Phase 6 adds real biometric and alert consultation to the psychologist Patient
Workspace in `admin-web`. It is limited to data already persisted by `server`:
synced biometric summaries and persisted alerts, including the mobile SOS flow.

It does not create a biometric-anomaly-to-alert pipeline, notification system,
clinical interpretation, patient-specific thresholds, new mobile experience, or
AI inference integration.

## 2. Current real architecture

```text
Mobile biometric samples
  → local SQLite (high-frequency samples, retained for 48 hours)
  → hourly aggregate of unsynced samples (at least five samples; at most 120 selected)
  → POST /api/v1/biometrics/summary
  → BiometricRecord in server

Mobile SOS confirmation
  → POST /api/v1/alerts (or the offline sync queue)
  → Alert in server with type panic_button and status new
  → psychologist consults it from admin-web in a later subphase
```

The sync request sends `studentId`, `windowStart`, `windowEnd`, average and
maximum heart rate, average stress and oxygen, `totalSteps`, and
`anomalyEpisodesCount`. The server currently persists only the supplied average
heart rate, average stress, optional average oxygen (defaulting to 98 when
omitted), and `windowEnd` as the record timestamp. It derives the patient under
RLS when no `studentId` is sent.

These records are synchronized summaries, not live telemetry. A recent record
does not establish that an ECOS Band is currently connected.

## 3. What ECOS currently does not do

- It does not create an `Alert` automatically from a biometric threshold,
  local anomaly result, or red/yellow/green state.
- It does not persist or use `anomalyEpisodesCount`.
- It does not send therapist push notifications, email, SMS, WebSocket, or SSE
  notifications for alerts.
- It does not have patient-specific biometric ranges or configurable baselines.
- It does not execute `assets/model.pte` through ExecuTorch. The mobile
  `ExecuTorchService` can load the JavaScript/native module when available, but
  never loads the model asset or calls a native inference API; the active result
  is calculated from manual MSE and threshold logic.

`Alert` is a persisted event. A notification is an active delivery mechanism;
the latter is not currently part of ECOS.

## 4. Mobile biometric flow

`useBiometricMonitor` receives BLE values or the explicit demo simulator,
calculates stress from heart rate and activity, and stores local samples through
`saveBiometricSample`. SQLite stores `bpm`, `activity`, `spo2`, `stress_level`,
`mse_error`, `is_anomaly`, timestamp, and sync state.

`SyncDispatcher.aggregateAndSyncHourlySummary` aggregates unsynced local rows
and posts the summary. Successful synchronization marks the selected timestamp
window as synchronized. Network failures do not create server alerts; they only
leave or enqueue synchronization work.

The local `GREEN`, `YELLOW`, and `RED` classification is generated by manual
MSE, heart-rate, activity, and consecutive-alert rules. It is a mobile-local
presentation/action signal. `RED` can recommend opening the emergency modal,
but it does not itself submit an `Alert`.

## 5. Mobile SOS flow

The panic modal is an explicit user action with a five-second confirmation
countdown or a direct confirmation tap. It posts to `POST /api/v1/alerts` with:

```ts
{
  alertType: "panic_button",
  priority: "critical",
  contextSummary: "... current BPM, stress, and activity ...",
  biometricRecordId: null,
}
```

It deliberately omits `studentId`; the server resolves the authenticated
student profile. If the direct request fails, the same payload is queued for
later synchronization. The server creates an `Alert` with `status: new`,
`priority: critical` (also its default when priority is omitted), and a
description derived from the context summary or the SOS fallback text.

The mobile modal currently says it will notify the clinical team, but no active
notification transport is implemented. The persisted alert is the only verified
server-side result.

## 6. Backend biometric model

`BiometricRecord` belongs indirectly to a patient through
`BiometricRecord.deviceId → BandDevice.studentId → StudentProfile`.

| Persisted field | Current meaning/source |
| --- | --- |
| `id`, `deviceId` | Record and associated band identifiers. |
| `avgHeartRate` | Synced hourly average heart rate. |
| `stressLevel` | Synced calculated average stress. |
| `bloodOxygen` | Synced average oxygen when supplied; otherwise the current service default. |
| `timestamp` | The mobile summary `windowEnd`, not a real-time receipt signal. |
| `createdAt`, `updatedAt` | Database lifecycle timestamps. |
| `sleepQualityHours`, blood pressure fields, `bodyTemperature` | Nullable schema fields, not populated by the current mobile summary flow. |

There is an index on `deviceId`. There is not currently an index directly on a
patient plus timestamp because patient ownership is reached through the band
relation. Phase 6.2 must review an actual query plan before introducing an
index or denormalizing ownership.

## 7. Backend biometric APIs

All endpoints use the existing RLS transaction. Under the current policy, only
the owning student and currently assigned psychologist can access biometric
records; administrators are denied by the Phase 5 clinical-read restriction.

| Method | Path | Current contract |
| --- | --- | --- |
| `POST` | `/biometrics/summary` | Ingests one aggregate summary. The authenticated student can omit `studentId`; RLS remains authoritative. |
| `GET` | `/students/:studentId/bands` | Lists visible band-device rows, newest first. |
| `GET` | `/students/:studentId/biometrics?range&skip&take` | Returns `{ latest, data, meta }`; `range` accepts `24h`, `7d`, `30d`, or `90d` and filters only `data`/`meta`. `latest` remains all-time. List items contain only the three phase-6.1 metrics, `timestamp`, `createdAt`, and ID. `take` is validated from 1 to 100. |
| `GET` | `/students/:studentId/biometrics/summary?range` | Returns descriptive counts, average/minimum/maximum, and a bounded ascending aggregate series. `24h` uses local-hour buckets; `7d`, `30d`, and `90d` use local-day buckets. |
| `GET` | `/students/:studentId/alerts?skip&take&status&alertType&priority` | Returns a minimized paginated persisted-alert history. It verifies the visible patient first, orders by creation date and ID descending, and returns the institution timezone. |
| `GET` | `/students/:studentId/alerts/:alertId` | Returns a patient-qualified alert detail for an authorized psychologist. It includes only the workspace summary, persisted SOS context, lifecycle metadata, and actor summaries required by the detail page. |
| `GET` | `/students/:studentId/biometrics/latest` | Returns the newest record or `404` when none is visible. |
| `GET` | `/students/:studentId/biometrics/trends?from&to` | Returns ascending daily averages; defaults to the last 30 days. |

Phase 6.1 replaces the old bare history array with its validated pagination
envelope. Phase 6.2 uses the same preset-range resolver for history and a new
server-side parameterized aggregation for the web summary. It verifies the
visible `StudentProfile` before each request, computes the latest row
independently from pagination and ranges, and orders history by timestamp,
creation time, then ID. The mobile-compatible `trends?from&to` array contract
is preserved.

## 8. Alert model

`Alert` has optional `studentId` and `biometricRecordId`, `alertType`, short
`description`, `contextSummary`, `priority`, `status`, `resolved`,
`reviewedAt`, `reviewedById`, `closedAt`, `createdAt`, and `updatedAt`.

Alert types are `panic_button`, `biometric_anomaly`, and `ai_risk`; enum
availability is not evidence that all types have an active producer. The only
verified mobile producer in this audit is `panic_button` through SOS. Priorities
are `low`, `medium`, `high`, and `critical`; statuses are `new`, `reviewed`,
`in_follow_up`, and `closed`.

`AlertAction` preserves therapist lifecycle actions with `alertId`, `studentId`,
`therapistId`, a validated action type, optional comment, and `createdAt`.
Existing alert indexes cover `studentId`, `biometricRecordId`, `reviewedById`,
and `(studentId, status, createdAt)`.

## 9. Alert APIs and workflow

| Method | Path | Current contract |
| --- | --- | --- |
| `POST` | `/alerts` | Creates a persisted alert; RLS resolves/authorizes the patient. No alert-created audit event exists today. |
| `GET` | `/alerts?studentId&status&skip&take` | Visible alerts, newest first, as a bare array. |
| `GET` | `/students/:studentId/alerts?skip&take&status&alertType&priority` | Visible patient alerts as a minimized `{ data, meta }` envelope, newest first. It validates pagination and enum filters, then returns `404` before querying alerts when the patient is not visible. |
| `GET` | `/students/:studentId/alerts/:alertId` | Patient-qualified detail for psychologists. It verifies the visible patient and the `Alert → StudentProfile` relation inside RLS; unavailable, mismatched, or inaccessible resources return `404`. |
| `GET` | `/alerts/:id` | Full alert with its actions when visible. |
| `GET` | `/alerts/:id/actions?skip&take` | Oldest-first actions when visible. |
| `PATCH` | `/alerts/:id/review` | Psychologist-only; only `new` alerts; writes `reviewed` plus an `AlertAction` and `ALERT_REVIEWED` audit metadata. |
| `POST` | `/alerts/:id/actions` | Psychologist-only; requires a reviewed/non-closed alert. The first action changes `reviewed` to `in_follow_up`. |
| `PATCH` | `/alerts/:id/close` | Psychologist-only; requires reviewed or in-follow-up state; writes `closed`, `closedAt`, `resolved: true`, and a closing action. |

There is no transition from `closed` back to an active state. A new alert must
be reviewed before it can receive an action or be closed. Administrators do not
have alert visibility or lifecycle authority. Students retain self-read and
self-create visibility through RLS; the future portal routes remain
psychologist-facing.

## 10. Permissions and privacy

`biometrics.view` and `alerts.view` already exist for the psychologist role in
`admin-web`. Phases 6.1–6.2 enable **Biometría** and Phase 6.3 enables
**Alertas**.
The biometric history endpoint has a psychologist-or-student role guard, so
administrators receive `403`; RLS then limits the record scope to the owner or
currently assigned psychologist. `alerts.manage` is available to psychologists
for later review, actions, and closing. Server guards and RLS, not route
permission alone, are authoritative.

Clinical payloads, SOS context, and detailed biometric records must never be
logged to the browser console, analytics, or persistent browser storage. URLs
may contain only patient identifiers and non-sensitive list state such as page,
date range, and alert status. Former assignment ownership does not grant a
general history right: Phase 6 uses the current RLS policy unless a later,
separately-reviewed continuity requirement changes it.

## 11. Patient routes and workspace integration

The reserved route helpers already exist. The following routes are planned and
will reuse `PatientWorkspace`, a verified patient context, shared empty/error
states, and the institution timezone:

- `/patients/[id]/biometrics`
- `/patients/[id]/alerts`
- `/patients/[id]/alerts/[alertId]`

Phases 6.1–6.2 enable `/patients/[id]/biometrics`, its exact navigation item,
route-access rule, breadcrumb, URL pagination, preset-range selector,
descriptive summary cards, and accessible line charts. They do not change
Patient Overview. Phase 6.3 enables `/patients/[id]/alerts` with a paginated,
filterable timeline of persisted alerts. Phase 6.4 adds its patient-qualified
detail route plus controlled review and closure; notifications and realtime
behavior remain out of scope.

## 12. Query key strategy

`features/biometrics` uses:

```ts
biometricKeys.all
biometricKeys.byPatient(patientId)
biometricKeys.history(patientId, filters)
biometricKeys.summary(patientId, range)
```

Phase 6.3 adds `features/alerts` with:

```ts
alertKeys.all
alertKeys.byPatient(patientId)
alertKeys.list(patientId, filters)
alertKeys.detail(patientId, alertId)
```

Mutations in Phase 6.4 will invalidate the affected alert detail/list and the
patient overview; no biometric read query should be invalidated by an alert
lifecycle change.

## 13. Backend changes required

Phases 6.1–6.2 add the validated biometric list/summary DTOs and minimized
Swagger response envelopes. They make no Prisma schema, index, migration,
mobile, or alert changes. The actual `EXPLAIN (ANALYZE, BUFFERS)` review for a
possible `(device_id, timestamp)` index remains required in an environment
with representative data; the local Supabase stack was unavailable during this
implementation.

Before each consuming UI subphase, verify whether its exact UX requires:

- validated query DTOs and `{ data, meta }` envelopes for biometric and alert
  lists;
- patient verification before list queries, so inaccessible resources use the
  established anti-enumeration response rather than an ambiguous empty array;
- minimized list DTOs instead of returning `contextSummary` and alert-action
  comments in histories;
- a patient-qualified alert detail endpoint for the portal; and
- database-side or bounded trend aggregation for a selected date range.

These are deferred so Phase 6.0 does not pre-build Phase 6.1–6.4 APIs.

## 14. Performance considerations

Use server pagination for raw biometric and alert history. Never download a
patient's full history for browser filtering or charting. Trends must always
use a bounded date range and should move grouping to a database aggregation if
query-plan/data-volume review shows the current in-service grouping is not
sufficient. Existing alert composite indexing already supports the principal
patient/status/recent order. No new index is justified by this audit alone.

## 15. Patient Overview and charts

`GET /students/:studentId/overview` returns one compact Phase 6.5 projection:
the stable latest biometric record with heart rate, numeric stress, oxygen and
its timestamp, plus `alertsSummary` with the exact non-closed count and at most
three minimized recent alerts. It does not return sleep, temperature, alert
descriptions, SOS context, trends or histories. The overview links to the
dedicated pages and makes no clinical interpretation or real-time claim.

`admin-web` already depends on `recharts` and defines chart color tokens. The
legacy `app/views/PatientDetail.tsx` charts use mock data and include unsupported
metrics such as blood pressure. Phase 6.2 must reuse Recharts primitives and
only real trend fields; it must not reuse mock data or claim clinical meaning.

## 16. Phase breakdown

1. **6.0 — Audit and foundations (complete):** document the actual mobile,
   server, authorization, performance, privacy, route, and chart boundaries.
2. **6.1 — Patient biometrics (complete):** `/patients/[id]/biometrics` shows
   the latest synchronized summary and recent paginated persisted records with
   a minimized backend envelope and neutral empty state.
3. **6.2 — History and trends (complete):** validated date ranges, bounded
   history, backend-compatible aggregation, and Recharts visualizations of
   actual heart rate, stress, and oxygen data without clinical inference.
4. **6.3 — Patient alert history (complete):** `/patients/[id]/alerts` for real
   persisted alerts, with privacy-minimized pagination and status/priority/type
   presentation. SOS is identified from `panic_button` only.
5. **6.4 — Alert detail and lifecycle (complete):**
   `/patients/[id]/alerts/[alertId]` reads a patient-qualified detail projection,
   supports server-authoritative review and closure, and keeps the existing
   `new → reviewed → in_follow_up → closed` transition rules. Detail access is
   psychologist-only; RLS preserves current-assignment scope and returns `404`
   for unavailable patient resources. Review and closure use conditional writes
   to return `409` on concurrent state changes, invalidate only the affected
   alert/patient-overview caches, and audit identifiers without SOS text.
6. **6.5 — Overview alignment (complete):** links and aligns the real latest
   biometric and open-alert summaries with the Phase 6 details, without
   manufacturing analysis or adding requests.
7. **6.6 — Integration and verification:** exercise access boundaries, list
   scale, date zones, cache invalidation, responsive behavior, and privacy.

## 17. Explicitly out of scope

- Automatic biometric alerts or threshold-triggered backend jobs.
- Patient-specific thresholds or baseline configuration.
- Persisting or displaying `anomalyEpisodesCount`.
- Persisting local `GREEN`/`YELLOW`/`RED` states as server alerts.
- ExecuTorch/model asset integration, server AI inference, or automatic AI
  anomaly detection.
- Push, email, SMS, WebSocket, or SSE therapist notifications.
- Mobile redesign or changes not required by a verified API contract.

## 18. Risks and Phase 6.1 readiness

The main risks are treating local mobile classification as a clinical alert,
overstating summary data as live monitoring, exposing SOS context in list views,
and using unbounded list/trend responses. The plan addresses them by preserving
the server as the data boundary and separating mathematical aggregation from
clinical interpretation.

Phases 6.0 through 6.3 are complete. The local Supabase stack was unavailable
for the Phase 6.2 real-data query-plan review, so an `EXPLAIN (ANALYZE,
BUFFERS)` review remains a prerequisite for any future biometric index change.
Phase 6.4 is complete. It preserves the same privacy, authorization, and
non-notification boundaries; generic follow-up action entry remains outside its
portal scope.
